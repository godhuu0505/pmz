# Grill Session: gatekeeper-mvp

開始: 2026-06-14
最終更新: 2026-06-14
ステータス: in-progress
ドメイン: ソフトウェア / AIエージェント（リリース判定ゲートキーパー × 自己改善）

## サマリー

PRマージ〜デプロイの2段ゲートで「リリースしてよいか」をエンジニアリング指標＋PM観点から
自律判定し、リリース結果から学習して判定精度を上げ続けるAIエージェント「GateKeeper（仮称）」。
本セッションでは、マージ済み要件定義書(`release-gatekeeper-agent-requirements.md`)で確定した
骨格を前提に、特に自己改善の機構・データ設計・要件充足判定・成功指標・リスクを深掘りする。

### DECIDED: 自己改善の正解ラベルの出どころ（B1）
- 決定: 学習の正解ラベルは客観基準に一本化する。
  - 承認したリリース → 客観アウトカム（①要件に合っていたか ②実際に障害が起きたか。定性/定量）
  - ブロックしたリリース → 観測不能なため人間が補助的にラベル付け
- 補足: 一度「人間の承認/ブロック判断そのものに寄せる」案を検討したが、
  実際の障害発生を正解とする当初方針と矛盾するため棄却。
- 補足: ブロックにより失敗データが減るのは「ゲートが効いている＝成功」とみなし、選択バイアスは許容。
- 根拠: 反実仮想問題を回避しつつ、客観的アウトカムを学習目標にできる。
- 日付: 2026-06-14

### DECIDED: 正解ラベルの独立性確保（B1）
- 決定: 承認リリースの「要件充足/障害」ラベルは、エージェント自身の判断とは独立に、
  リリース後の客観イベント（バグ/修正PR/ロールバック等）から自動導出する。
- 棄却: 事後ラベルをLLM判断で作る案は循環（自分の出力で自己学習＝確証バイアス/モデル崩壊）のため不採用。
- 残課題: イベントの帰属（どのイベントをどのリリースに紐づけるか）と計測ウィンドウの定義。
- 日付: 2026-06-14

### DECIDED: 客観イベントの帰属と観測ウィンドウ（B1）
- 決定: 帰属は (c) ハイブリッド = 明示リンク（revert/修正PR/Issueのリリース参照）優先、
  無ければヒューリスティック（時間ウィンドウ + 変更ファイルの重なり）で補助。
- 決定: 観測ウィンドウは 24時間。何も起きなければ「成功（障害なし）」と確定。
- 日付: 2026-06-14

### DECIDED: ラベルは2軸・別ウィンドウ（B1）
- 決定: 学習ラベルを2軸に分け、それぞれ別の確定ウィンドウを持つ。
  - 障害軸: 24時間で自動確定（上記）
  - 要件充足軸: より長いウィンドウ / 遡及ラベルで確定（具体メカニズムは要決定）
- 根拠: 要件未達は静かに遅れて顕在化するため、24hでは構造的に取りこぼす。
- 日付: 2026-06-14

### RESOLVED: 要件充足軸の確定メカニズム（B1ラベル設計 完了）
- 解消内容: (c) 暫定ラベル（楽観的に「充足」）→ 要件未達イベントが出たら遡及で「未達」修正
  → 上限30日到達で最終確定。
- これにより B1 の「正解ラベル設計」は完了（出どころ・独立性・帰属・2軸ウィンドウ・確定方式すべて確定）。
- 日付: 2026-06-14

### DECIDED: 学習機構（確定ラベルの反映方法）（B1）
- 決定: (d) 併用方式。
  - 記憶/Few-shot検索: 誤判定ケースをメモリに蓄積し、判定時に類似の過去ケースを検索して
    プロンプトに注入（即応・モデルは変えない）。
  - ルール自動進化: 振り返りエージェントが誤判定を分析し、新チェックルールをバージョン管理
    ルールブックへ追記（恒久化・審査映え）。
  - ファインチューニング(c)は締切的に非現実的のため不採用。
- 残課題: 自己生成ルールの暴走/矛盾/肥大化への防波堤（検証ゲート・廃止/重複排除）。
- 日付: 2026-06-14

### DECIDED: 自己生成ルールの検証ゲート（B1）
- 決定: (b) 新ルールは本番適用前に回帰テストで自動検証する。ラベル付き過去データセットで
  バックテストし、「精度が下がらない／誤ブロックを増やさない」ものだけ採用。
  元要件(C)評価データセットが暴走の防波堤＝ゲートとして機能。
- 日付: 2026-06-14

### RESOLVED: ルールのライフサイクル管理（B1 完了）
- 解消内容: 肥大化・矛盾対策を3段で持つ。
  - ① 入口の重複排除: 新ルール追加前に既存と意味的重なりを照合し、統合 or 棄却。
  - ② 最小限の優先順位: ルールにメタ（重大度/スコープ/block・allow種別）を持たせ衝突を解決。
    解決不能は人間へ。
  - ③(a) 性能ベース廃止: 発火率・的中率を記録し、回帰データセットで精度に寄与しないルールを
    自動廃止候補に。
  - ③(c) 定期棚卸し（庭師ジョブ）は審査映えのため採用。TTL(b)は見送り。
- これにより B1「自己改善の機構」全体が解消（ラベル設計／学習機構／検証ゲート／ルール管理）。
- 日付: 2026-06-14

## 確定要件（ドラフト）

### 背景・目的
- リリースのGo/No-Go判断は、コード・CI・本番メトリクス・要件充足・リリースノートなど散在情報を
  かき集める属人的作業で、見落としが障害を生む。これをエンジニアリング指標＋PM観点の両面から
  自律判断し、リリース結果から学習して精度を上げ続けるAIエージェントで代替する。

### スコープ（MVP）
- ゲート: ① PRマージゲート（MVP）。② デプロイ前ゲートはPhase2。
- 入力シグナル: コード変更 / CI結果 / 要件充足（要件定義書ベース）。本番メトリクスはPhase2。
- 出力: 条件付き自律（低=自律実行 / 中=人間承認 / 高=自律ブロック）。
- デモ: 合成リリース履歴（手作り ~24件）で自己改善の前後比較を可視化。

### 自己改善ループ（B1で確定）
- **正解ラベル**: 客観基準。承認分は客観イベントから自動導出、ブロック分は人間が補助ラベル。
  事後ラベルはLLM判断で作らない（循環回避）。
- **帰属**: 明示リンク優先 + ヒューリスティック補助。
- **2軸ウィンドウ**: 障害軸=24h自動確定 / 要件充足軸=暫定→遡及修正→上限30日確定。
- **学習機構**: 記憶/Few-shot（即応）+ ルール自動進化（恒久化）。FTは不採用。
- **検証ゲート**: 新ルールは回帰テスト（ラベル付き過去データのバックテスト）通過後に有効化。
- **ルール管理**: 入口の重複排除 + 最小限の優先順位 + 性能ベース廃止 + 定期棚卸し。

### 合成データ設計（B2で確定）
- 生成方式: 手作り・小規模（~24件）。MVP後にLLM生成で増量余地。
- 失敗アーキタイプ: (i) DBマイグレーション系 + (ii) 要件未達系。各型を「見逃す→ルール化→検知」の3幕で。
- レコードスキーマ: 識別 / 入力シグナル(code,ci,requirement) / post_events /
  labels(incident_axis, requirement_axis, correct_verdict) / arc メタ。
  - `correct_verdict` は合成データ前提（実運用では成立しないと明記）。`metrics_baseline` はMVP省略。
- アーク: ベースライン→型(i)地雷→学習→正常→型(ii)地雷→学習→再来検知、の時系列。
