ハッカソン審査基準（課題の新規性／解決策の有効性／実装品質と拡張性／DevOpsサイクル）

## 1. コンセプト（一行サマリー）

> **「リリースしていいか？」を、エンジニアリング指標とPM観点の両面から自律判断し、
> リリース結果から学習して判定精度を上げ続ける、AIリリースゲートキーパー。**

製品名: **`pmz`**（全小文字・単一トークン）

### 1.1 名称 `pmz` の由来（命名の言語化）

`pmz` は3文字に複数の意味を重ねた多義的な名前。中核は **PM観点 × Z軸**。

- **PM = PM観点（Product perspective）** — このプロダクト**最大の差別化**そのもの（§3.2）。
  既存のCIゲートが見ない「PRの変更が要件（＝プロダクトの意図）を満たしているか」を判定する。
  名前の先頭に PM を置く必然性がここにある。
- **z = Z軸（自己改善の時間軸）** — エンジニアリング指標(X)とPM観点(Y)の二次元評価に、
  **過去のリリース結果から学習して賢くなる第3の軸(Z)** を足したのがこの製品（§3.3 の自己改善ループ）。
  静的な2D評価を超えて時間方向に進化することを一文字で表す。
- **PMz（vector の z 成分）** — PM観点という定性判断を、**定量軸(z)へ射影して測定可能にした**もの。
  混同行列で精度を測る設計（§6.1）と整合する。「PM観点をエンジニアリングの言葉で計測する」を含意。

> **一行**: 「PM観点でリリースを判定し、結果から学習して時間軸（Z軸）で賢くなり続けるゲートキーパー」。

補強的な多義（ピッチで出し分け可能）:
- **音の連想**: `pmz ≈ promise`（要件＝チームへの「約束」を守れているか）／`pmz ≈ premise`（リリースの「前提」が揃っているか）。
- **バックロニム**: **P**re-**M**erge **Z**ero（プレマージでゼロインシデント＝MVPスコープ §3.1・誤承認率を下げる §6 に直結）。
- **積メタファー**: Go = **P · M · Z > 0**（製品/要件・メトリクス/CI・学習知見のどれか一つでも 0 なら No-Go）。

> 📌 表記規約: ドキュメント・コード・設定では製品名を **`pmz`**（全小文字・単一トークン）で統一する。
> 旧仮称 `GateKeeper` は廃止。一般名詞としての「ゲートキーパー（門番）」は引き続き役割の説明に用いる。

## 2. 課題設定（なぜこれが刺さるか）

### 2.1 ペルソナと痛み

| ペルソナ | 痛み |
|----------|------|
| **リリース判断者（テックリード/EM/PM）** | リリースのGo/No-Goを、PR diff・CI結果・本番メトリクス・要件充足・リリースノートなど**散らばった情報を毎回かき集めて**判断している。属人的で、見落としが障害につながる。 |
| **PM/プロダクトオーナー** | 「この変更は要件を満たしているか」「リリースノートは正しいか」「事業リスクは」を、エンジニアの報告に依存して判断せざるを得ない。 |
| **オンコール/SRE** | 「なぜこのリリースが通ってしまったのか」を障害後に振り返るが、**判断基準が更新されず同じ失敗を繰り返す**。 |

### 2.2 なぜAIエージェントでなければ解けないのか（必然性）

- 判断材料が**マルチソース・マルチモーダル**（コード/テキスト/時系列メトリクス/履歴DB）で、ルールベースでは表現しきれない**文脈判断**が必要。
- 「リリース可否」は**複数ステップの調査 → 統合 → 判断 → 検証**を要するタスクであり、単発のLLM呼び出しでは完結しない（＝エージェントの必然性が高い）。
- 「自己改善」＝**過去の判断結果から学習**するには、判断・記録・振り返り・基準更新を自律的に回すループが必要。これはエージェント以外では成立しない。

> 審査軸との対応: 「課題の新規性」＝PM観点まで含むリリース判定は前例が少ない／「エージェントの必然性」を構造的に満たす。

## 3. スコープ（決定事項）

### 3.1 ゲートの配置 ✅ 決定

**2段ゲート構成**（DevOpsサイクル全体をカバー）:

```
[開発] --PR--> ①PRマージゲート --merge--> [CI/CD] --> ②デプロイ前ゲート --deploy--> [本番]
                     ↑                                        ↑                          │
                     │                                        │                          │
                     └──────────── 自己改善ループ ←─── ③リリース結果の観測 ←───────────┘
```

- **① PRマージゲート**: PRに対し「マージしてよいか」を判定。diff・CI結果・要件充足・レビュー状況を見て、コメント＋判定を返す。
- **② デプロイ前ゲート**: CI/CDパイプライン内で「本番に出してよいか」を判定。直前のGo/No-Go。
- **③ 結果観測 → 自己改善**: デプロイ後の本番メトリクス／障害発生／ロールバック有無を観測し、過去判定にラベル付けして学習に回す。

### 3.2 判定シグナル ✅ 決定（PM観点を含む）

| カテゴリ | シグナル | データ源（想定） |
|----------|----------|------------------|
| **コード** | diff規模・変更ファイル・高リスク箇所（認証/決済/DB migration等） | GitHub API / git diff |
| **テスト/CI** | テスト成否・カバレッジ・Lint・ビルド・セキュリティスキャン | GitHub Actions / Cloud Build |
| **本番運用** | エラー率・レイテンシ・リソース使用率・直近の安定性 | Cloud Monitoring / Logging |
| **DORA / Four Keys** | デプロイ頻度・変更リードタイム・変更失敗率・MTTR | BigQuery（履歴集計） |
| **履歴** | 過去の類似リリースとその結果（障害有無・ロールバック有無） | Firestore / BigQuery |
| **PM観点** | 要件充足度・リリースノートの妥当性・スコープ逸脱・事業リスク | **要件定義書（MVP）** → 将来: Issue / リリースノート / チケット |

> ★「PM観点（要件充足・リリースノート・事業リスク）」を判定材料に入れる点が他のCIゲートとの最大の差別化。
>
> **要件の取得元（決定）**: 将来的には GitHub Issue・リリースノート・チケット・要件定義書など複数ソースから取得する。
> ただし **MVPでは「要件定義書」を唯一のソース**とし、「PRの変更が要件定義書を満たしているか」を判定する。

#### 3.2.1 要件充足判定 詳細設計（grillセッション `gatekeeper-mvp` で確定）

このプロダクト最大の差別化（PM観点）の核。ハルシネーションを構造的に抑止する設計とする。

- **受け入れ基準の正本化**: 要件定義書は散文のため機械チェック不能。エージェントが
  **構造化書式で受け入れ基準をドラフト抽出 → 人間が対話で確認・追記・確定** したものを
  「正本（canonical acceptance criteria）」とし、以降のチェック根拠とする。
  LLMが勝手に正本を書き換えない（人間確定が条件）。
- **トレーサビリティ（PR→要件）**: 申告（PR本文/ラベルの対応要件ID）を正とし、無ければ
  diff/コミットから推論して候補提示。さらに **申告と実装の食い違い**（"要件X対応"と言うのに
  diffが別物）を検知して指摘（要件未達アーキタイプ(ii)と直結）。
- **充足判定**: 各受け入れ基準について diff/テスト/PR説明から**証拠を引用**し、
  `満たす / 満たさない / PRからは検証不能` の3値＋確信度を出す。
  **「検証不能」は断定せず人間にエスカレーション**（棄権を許す＝ハルシネーション抑止の本質、
  条件付き自律と接続）。
- **部分充足**: MVPはPR単位で「申告した基準」だけを評価し**途中PRは止めない**。要件全体の完了は
  基準カバレッジを横断集計で別管理。リリースノートと基準の整合チェック（"対応済"主張 vs 未達）は
  **Phase2のデプロイ前ゲート**で実施。

### 3.3 自己改善の方式 ✅ 決定（総合型）

3つの学習メカニズムを統合する:

1. **(A) リリース結果からの学習**
   過去判定を「正解/誤判定」でラベル付け（誤承認＝障害を通した／誤ブロック＝良いリリースを止めた）し、
   誤判定ケースをメモリ／Few-shot事例として次回判定に注入。
2. **(B) 判定基準ルールの自動進化**
   障害発生時に「振り返りエージェント」が原因と見落とし観点を分析し、**新しいチェックルールを提案・バージョン管理**して追加。
3. **(C) 評価データセット＋回帰テスト（LLMOps）**
   ラベル付き過去リリースを評価データセット化し、プロンプト/モデル変更時に**判定精度を自動評価**（回帰テスト）。

> メタ指標として「判定精度・誤承認率・誤ブロック率の時系列推移」を可視化し、
> **"エージェントが賢くなっている"こと自体をデモで見せる**（審査チェックリスト#6 LLMOpsに直結）。

#### 3.3.1 自己改善ループ 詳細設計（grillセッション `gatekeeper-mvp` で確定）

**(1) 正解ラベルの出どころ**
- 学習の正解ラベルは**客観基準に一本化**する。
  - 承認したリリース → 客観アウトカム（①要件に合っていたか ②実際に障害が起きたか）を
    リリース後の客観イベントから**自動導出**。
  - ブロックしたリリース → 観測不能（反実仮想）なため**人間が補助的にラベル付け**。
- 事後ラベルをLLM判断で作ることは**禁止**（自分の出力で自己学習＝確証バイアス/モデル崩壊の回避）。
- ブロックにより失敗データが減るのは「ゲートが効いている＝成功」とみなし、選択バイアスは許容。

**(2) イベントの帰属と確定ウィンドウ（2軸）**
- 帰属: **明示リンク優先**（revert/修正PR/Issueのリリース参照）+ 無ければ**ヒューリスティック補助**
  （時間ウィンドウ + 変更ファイルの重なり）。
- **障害軸**: 24時間で自動確定（イベントが出なければ「障害なし」）。
- **要件充足軸**: 暫定ラベル（楽観的に「充足」）→ 要件未達イベントで遡及修正 → 上限30日で最終確定。
  （要件未達は遅れて顕在化するため、24hでは構造的に取りこぼす非対称性への対応）

**(3) 学習機構（確定ラベルを次回判定へ反映）**
- **記憶/Few-shot検索**: 誤判定ケースを蓄積し、判定時に類似の過去ケースを検索してプロンプトに注入
  （即応・モデルは変えない）。
- **ルール自動進化**: 振り返りエージェントが誤判定を分析し、新チェックルールをバージョン管理
  ルールブックへ追記（恒久化・審査映え）。
- ファインチューニングは締切的に非現実的のため**不採用**。

**(4) 自己生成ルールのガバナンス（暴走防止）**
- **検証ゲート**: 新ルールは本番適用前に**回帰テスト**（ラベル付き過去データのバックテスト）を通過した
  ものだけ採用。「精度が下がらない／誤ブロックを増やさない」ことを確認（元要件(C)が防波堤）。
- **ルール管理**: ① 入口の重複排除（意味的重なりを統合/棄却）+ ② 最小限の優先順位（重大度/スコープ/
  block・allow種別で衝突解決、解決不能は人間へ）+ ③ 性能ベース廃止（発火率・的中率で剪定）
  + ④ 定期棚卸し（庭師ジョブ）。

### 3.4 出力・アクション ✅ 決定（条件付き自律）

リスクに応じて自律度を変える **「条件付き自律（Conditional Autonomy）」** を採用:

| リスク判定 | エージェントの挙動 |
|------------|--------------------|
| 低リスク（高信頼でGo） | **自律実行**（PR承認 / デプロイ実行） |
| 中リスク | 判定＋根拠レポートを提示し、人間に承認を促す（Human-in-the-loop） |
| 高リスク（No-Go） | **自律ブロック** ＋ 理由・該当箇所・改善提案を提示 |

採用理由: 「完全自律」は審査での自律性アピールは強いが本番では危険、「提示のみ」は自律性が弱い。
**条件付き自律はリスクに応じて自律度を変える設計**で、「本番品質」と「エージェントの必然性」を両立できる。

> どの閾値で自律実行/エスカレーションを分けるか（信頼度スコア・リスクレベルの境界）は、
> 自己改善ループ(C)の評価データで継続調整する対象とする。

## 4. アーキテクチャ（想定 / GCP前提）

### 4.1 マルチエージェント構成（ADK想定 ＝ 審査で王道）

```
                    ┌─────────────────────────────┐
                    │   Orchestrator Agent        │  ← 全体統括・最終判定の統合
                    │   (Gemini + ADK)            │
                    └──────────────┬──────────────┘
        ┌──────────────┬───────────┼───────────┬──────────────┐
        ▼              ▼           ▼           ▼              ▼
 ┌────────────┐ ┌────────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐
 │ CodeRisk   │ │ TestSignal │ │ OpsMetric│ │ PM/Req   │ │ Retrospective│
 │ Agent      │ │ Agent      │ │ Agent    │ │ Agent    │ │ Agent (改善) │
 │ diff解析   │ │ CI/カバレ  │ │ 本番監視 │ │ 要件充足 │ │ 障害振り返り │
 └────────────┘ └────────────┘ └──────────┘ └──────────┘ └──────────────┘
```

各サブエージェントが専門領域を評価 → Orchestratorがスコア統合して Go/No-Go を判定。
これにより「マルチステップ自律判断」「マルチエージェント協調」を構造的に実現。

### 4.2 GCPサービスマッピング（必須要件の充足）

| レイヤ | サービス | 役割 |
|--------|----------|------|
| 実行基盤（必須） | **Cloud Run** | エージェント本体・Webhook受信をホスト |
| AI（必須） | **Gemini API + ADK** | 判定推論・マルチエージェント |
| 永続化 | **Firestore** | 判定ログ・ルール・学習メモリ |
| 分析 | **BigQuery** | DORA/Four Keys集計・履歴分析・評価データセット |
| 観測性 | **Cloud Logging / Monitoring / Trace** | 本番シグナル取得・結果観測 |
| CI/CD | **Cloud Build + GitHub Actions** | パイプライン本体＋ゲート統合 |
| IaC | **Terraform** | インフラ再現性 |

## 6. 評価指標（KPI）

| 指標 | 意味 |
|------|------|
| 判定精度（Accuracy） | 過去リリースに対する Go/No-Go の正答率 |
| 誤承認率（False Approve） | 障害を起こすリリースを通してしまった率（最重要・低いほど良い） |
| 誤ブロック率（False Block） | 良いリリースを止めてしまった率 |
| 判定リードタイム | 判定にかかる時間（速いほどDevOpsを阻害しない） |
| **精度の時系列改善** | 自己改善が効いている証拠（デモの目玉） |

### 6.1 成功指標 詳細設計（grillセッション `gatekeeper-mvp` で確定）

- **枠組み**: 判定を2値分類（Go/No-Go vs `correct_verdict`）とみなし**混同行列**で測定。
  誤差は **F-beta** で重み付け（誤承認FPを主役にしつつ、誤ブロックFNの暴走も罰する）。
  → 「全ブロックで誤承認ゼロ」というズルい最適化を指標が褒めない歯止めを内蔵。
- **改善主張の妥当性（"そう作っただけ"批判への対策）**: ~24件の手作りデータは*循環*しやすいため、
  **デモは手作り制御ケース（アーク）**で分かりやすく見せ、**指標は学習に使っていないLLM生成の
  評価セット**で混同行列を出して裏付ける（役割分担し両方を正直に提示）。
- **計測構造**: **学習前後の混同行列（before/after）** を生成セットで対比 ＋ 手作りアークの**時系列グラフ**。
- **目標KPI（相対目標主体）**:
  1. **誤承認率の削減幅** — 学習前比で大幅削減（具体%は初回ベースライン測定後に確定）。
  2. **再発アーキタイプの検知率 = 100%** — 学習済みの型(i)(ii)再来は必ず検知（唯一100%と言える強KPI・デモの山場）。
  3. **誤ブロック率を悪化させない** — F-betaが学習前比で改善（健全性の担保）。

## 7. リスク・失敗モードと安全設計（grillセッション `gatekeeper-mvp` で確定）

「本番品質」を担保するための失敗モード対策。自律性を出しつつ実運用で破綻しない設計とする。

| # | 失敗モード | 対策（決定） |
|---|------------|--------------|
| 1 | 緊急時にゲートが邪魔をする | **緊急バイパス**: 人間がemergencyフラグでスキップ可。全て記録し、事後にエージェントがレビューして学習ループに回す。 |
| 2 | ゲート自体が落ちる（応答不能/LLM API障害） | **fail-to-human**: 自動判定を外し従来の人間レビューに縮退。ブロックも素通りもせず単一障害点化を回避。 |
| 3 | プロンプトインジェクション（PR本文/diff/コミットの指示注入） | **多層防御**: ①入力を信頼できないデータとして構造的に隔離 ②注入検知を赤旗化しエスカレーション ③**権限分離**（読むエージェントに承認権限を与えず、判定は構造化シグナルからのみ＝注入文だけで覆せない）。 |
| 4 | 誤承認の責任分界 | エージェントは**委譲された低リスク範囲で動く道具**で最終責任は人間/チーム ＋ **全判定の改ざん不能な監査証跡**（入力/判定/確信度/根拠/発火ルール/モデルバージョン＝追跡・再現・巻き戻し可能）＋ 自律はロールバック可能な範囲に限定。 |
| 5 | 自律パスでの自信満々の誤判定（ハルシネーション） | **多層**: 確信度≥T かつ 客観ゲート全緑（CI通過・高リスクフラグなし・受け入れ基準が"検証不能"を含まず充足）のみ自律承認 ／ 迷えば人間 ／ **決定論的ハードガード**（決済・認証・DBマイグレーション等の高リスク領域はLLMの確信度に関係なく自律承認禁止＝被害上限をアーキで固定）。 |

> #5 のハードガードは失敗アーキタイプ(i)(DBマイグレーション)と直結。確信度はLLMの自己申告で
> ハルシネーション時には確信度も嘘になり得るため、LLMが覆せない決定論的な壁を別に持つことが肝。

## 8. 段階的実装計画（MVP → 拡張）

| フェーズ | 内容 | 狙い |
|----------|------|------|
| **MVP** | ① PRマージゲートのみ。シグナルは **コード + CI + 要件充足（要件定義書ベース）**。「PRの変更が要件定義書を満たしているか」を判定し、Go/No-Go＋根拠コメントを返す。判定ログをFirestoreに記録。 | 動く骨格を最速で。エージェントの必然性とPM観点の差別化を最初に立てる |
| **Phase 2** | ② デプロイ前ゲート＋本番メトリクス観測＋DORA集計。マルチエージェント化（ADK）。 | DevOpsサイクル全体をカバー |
| **Phase 3** | ③ 自己改善ループ（結果ラベリング→学習→ルール進化→回帰テスト）。精度推移ダッシュボード。 | 「自己改善」「LLMOps」の証明・デモの目玉 |
| **仕上げ** | Terraform / 観測性 / コスト可視化 / 提出記事・アーキ図・デモ動画 | 本番品質と提出物の質 |

### 8.1 非機能・制約と実装優先順位（grillセッション `gatekeeper-mvp` で確定）

> 注: grillで MVP の中身を再定義した。**自己改善の核はMVP必須**（上表の粗いPhase分けより本節が優先）。

**非機能**
- **レイテンシ**: 非同期・数分以内（PRに対しGitHub Checkとして返す。CIと同列の体験）。
- **コスト管理**: スコープ外（既存決定）。

**スコープの線引き**
- **MVP must-have**: ①PRマージゲート本体（code+CI+要件充足→Go/No-Go＋根拠をGitHub Check）
  ②自己改善の核（記憶/Few-shot＋ルール進化で「見逃す→学習→検知」）③合成データ~24件＋
  before/after指標 ④決定論的ハードガード ⑤権限分離＋監査ログ ⑥マルチエージェント**4体**
  （オーケストレータ＋CodeRisk＋PM/Req＋Retrospective）。
- **Phase2送り**: デプロイ前ゲート②／本番メトリクス・DORA／リリースノート整合チェック／
  ルール回帰テスト自動ゲート・重複排除・性能ベース廃止・定期棚卸し（MVPはルール追加まで・検証は簡易）／
  インジェクション検知分類器（隔離＋権限分離はMVP）／2段階レイテンシ最適化／自動緩和バイパス／
  LLM生成の大規模評価セット／フル6エージェント。

**制約・体制**: 1人フルコミット、実働約4週間（6/14→7/10）。

**実装優先順位（デモ死守の順 / 1人想定）**

| 週 | 最優先 | 死守ライン |
|----|--------|-----------|
| W1 (〜6/20) | PRゲート骨格（GitHub Check/Cloud Run/Gemini、単一オーケストレータ） | 「ゲートが動く」 |
| W2 (〜6/27) | 合成データ~24件＋自己改善の核（見逃す→学習→検知） | **★作品の心臓・最優先死守** |
| W3 (〜7/4) | 4エージェント化(ADK)/ハードガード/権限分離・監査ログ/before-after指標 | 余力に応じて |
| W4 (〜7/10) | Terraform・観測性・記事・デモ動画 | 提出物の質 |

> 時間が逼迫したら、W3の4エージェント化を削ってでも**「自己改善が見えるデモ＋指標」を守る**
> （審査の"映え"はマルチエージェントの体裁より「賢くなる様子」が強いため）。

## 9. デモ題材（決定: 合成データ）✅

自己改善が効いていることを見せるためのデモは、**合成データ（疑似リリース履歴）** で構成する。

- **生成物**: 過去N件分の「PR diff / CI結果 / 本番メトリクス / 要件・リリースノート / 実際の結果（障害有無・ロールバック有無）」をセットにした疑似リリース履歴データセット。
- **設計方針**:
  - 障害を起こした"地雷リリース"と、安全なリリースを混在させ、**判定の正解ラベル**を仕込む。
  - 自己改善の効果を見せるため、「最初は見逃すが、結果を学習した後は同種を検知できる」**ストーリー性のあるシナリオ**を用意する。
  - DORA/Four Keysの時系列も合成し、メトリクス観測パスを通せるようにする。
- **利点**: 実運用データに依存せず、デモで**自己改善の前後比較（精度の向上）を再現性をもって見せられる**。締切7/10にも間に合いやすい。

### 9.1 合成データ 詳細設計（grillセッション `gatekeeper-mvp` で確定）

**生成方式**: 手作りシナリオ・小規模（**~24件**）。MVPは「改善が見える最小デモ」を最速で作り、
MVP後にLLM生成でノイズ/件数を増量する余地を残す。

**再発する失敗アーキタイプ（MVPは2本柱）**:
- (i) **DBマイグレーション系**（DevOps映え）
- (ii) **要件未達系**（PM観点の差別化・目玉）
- 各型を「①見逃して障害 → ②振り返りでルール化 → ③同型を検知してブロック」の3幕で仕込む。
- 拡張(MVP後): (iii) 依存・設定漏れ系、(iv) 高リスク領域×薄いテスト系、複数サービス横断障害。

**1リリースレコードのスキーマ**:
```
release_record:
  id / pr_number / commit_sha / timestamp / author
  code:        diff要約, 変更ファイル, リスクフラグ(DB migration/認証/決済), 変更行数
  ci:          test成否, カバレッジ, lint, build, security_scan
  requirement: 対象要件ID(要件定義書), 受け入れ基準, リリースノート本文
  post_events: [ {type: revert|fix_pr|incident|error_spike|requirement_miss_bug,
                  timestamp, linked_sha, touched_files} ]
  labels:
    incident_axis:    {value: ok|fail, window: 24h, confirmed_at}
    requirement_axis: {value: met|unmet, status: provisional|final, finalized_at}
    correct_verdict:  Go|No-Go   # 評価/回帰テスト用の"あるべき判定"
  arc: {archetype: db_migration|requirement_miss, act: 1_trap|2_learn|3_catch,
        recurrence_group_id}
```
- `correct_verdict` は**合成データだから正解を仕込む前提**（実運用では成立しない旨を明記）。回帰テストの土台。
- `metrics_baseline` は**MVPでは省略**（本番メトリクスはPhase2のデプロイ前ゲート管轄）。

**アーク構成（~24件のタイムライン）**:
- `#1–6` ベースライン正常承認 → `#7` 型(i)地雷→見逃し→24h障害→ルール化→回帰通過
  → `#8–11` 正常（誤ブロックが増えない確認）→ `#12` 型(ii)要件未達→見逃し→requirement_miss_bug→ルール化
  → `#13–18` 正常+ノイズ → `#19` 型(i)再来→検知ブロック → `#22` 型(ii)再来→検知ブロック → 残り正常。
- 効果: **誤承認↓・誤ブロック不変**を時系列グラフで示し、自己改善を可視化。
