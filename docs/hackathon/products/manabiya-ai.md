## ② 社会課題（なぜ刺さるか）

- **教師の業務過多**: 日本の教師は授業・授業準備に **週あたり約26.5時間** を費やしている、という背景を起点に課題設定。【確度中】
- **痛みの所在**: 授業「準備 → 運営 → 評価 → フィードバック」の全工程が属人的・高負荷。特に準備と採点・FBが重い。【確認済み】
- **教育DXの停滞**: 教育現場のIT導入が進まず、現場の変化への抵抗が強い。デジタル化は急務だが普及していない。【確度中】
- **既存AI授業支援の弱点**: 既存ツールは「教師の個性・経験」を反映できず、現場の反発・定着失敗を招きがち。→ ManabiyaAI は「教師の個性を保つ」ことを差別化に据える。【確度中】
- **前提環境**: 1人1台のデジタル端末（タブレット）が配布された対面授業環境を想定。【確認済み】

## ③ 解決内容と主要機能

「授業準備 → 運営 → 評価 → フィードバック」を一元化し、新人でも自分の個性を保ったまま高品質な授業を実現する包括支援。【確認済み】

1. **自動アジェンダ作成**: 学習指導要領（カリキュラム）と授業コマ数に基づき授業計画/アジェンダを自動生成。準備時間を大幅短縮。【確認済み】
2. **リアルタイム文字起こし & 端末同期**: 授業音声を Speech-to-Text でリアルタイム文字起こし。教師・生徒のタブレットに授業テキストを同期表示し、授業中の情報共有を強化。【確認済み】
3. **小テスト（クイズ）自動生成 + 自動採点**: 授業内容に基づき小テストを自動生成。選択式・穴埋め・自由記述など複数形式に対応、自動採点で効率化。【確認済み】
4. **理解度の可視化（思考プロセスの可視化）**: AI との対話で生徒の「思考プロセス」を可視化。教師は生徒の推論を分析し、どこで理解が躓いたかを特定して的を絞った指導が可能。【確認済み】
5. **教師の個性を反映したフィードバック**: 教師の過去授業データを学習し、好む説明方法・例を理解。FB を通じて情報を蓄積し、後続授業に個性が増していく形で反映。【確認済み】
6. **生徒ごとのパーソナライズ宿題・解説**: 各生徒に最適化した宿題と解説を提供。Gemini を使った個別学習支援の提案。【確認済み】
7. **理解度レポート**: 生徒ごとの理解度レポート/回答分析を作成。【確認済み】

## ⑤ 技術的工夫ポイント

- **マルチモーダル設計**: 音声（授業音声→文字起こし）＋テキスト（生成テキストの端末同期）＋生徒回答の分析を統合。入力モダリティをまたいで「授業ライブ → 即時教材化」を成立させている点が核。【確認済み（機能事実から）】
- **LangChain によるチェーン/エージェント構成**: アジェンダ生成・クイズ生成・採点・FB生成・宿題生成という**複数ステップのタスク連鎖**を LangChain で組んでいると推定。各機能が独立チェーン or ツール呼び出しになっている構成が自然。【推測】（一次記事403のため内部構成は未確認）
- **教師個性の継続学習ループ**: 過去授業データ＋教師FBを蓄積し、後続授業の出力に個性を反映していく「使うほど自分仕様になる」設計。これが「既存AIは個性を消す」批判への直接の回答であり、本作の差別化の中心。【確認済み】
- **なぜ ADK でなく LangChain か**: 一次記事に明示の理由は確認できず【推測】。一般論として、第1回（2024年度）時点では ADK が未成熟/未公開で、RAG・外部連携・チェーン記述に実績ある LangChain が現実解だったという文脈が考えられる（要・一次記事で裏取り）。

## ⑥ デモ / UX の見せ方と「85%削減」の根拠

- **UX の肝**: 教師・生徒タブレットでの**授業テキストのリアルタイム同期**。授業がそのまま教材・テスト・FBに変換される一気通貫の流れを見せる構成。【確認済み】
- **85%削減の主張（具体的な算出）**: 【確度中／複数スニペットで一致】
  - **1授業あたり**: 従来 **760分（約12時間40分）** → ManabiyaAI 導入後 **約113.67分（約1時間54分）**。→ **約85%削減**。
  - **採点**: 生徒1人あたり **従来15分 → 約1.17分**。
  - **学年全体（週次）**: 約 **215.43時間**の削減（**約84.9%**）。
- **評価**: 削減率の主張は「分単位の積み上げ試算」で具体的・定量的。ただし**前提条件（クラス規模/授業数/従来760分の内訳）の妥当性**は一次記事での検証が必要。試算ベースであり実測ではない可能性が高い点に注意。【推測】

## ⑧ pmz への学び

pmz =「AIリリースゲートキーパー」（PR を要件定義書に照らして Go/No-Go 判定し、結果から自己改善）の観点で、流用できる戦術と差別化示唆。

1. **定量効果を“分単位の積み上げ試算”で語る**【強く流用推奨】
   ManabiyaAI の「760分→113.67分＝85%削減」は、審査・ピッチで圧倒的に効く見せ方。
   pmz も「リリース判断者が毎回かき集める情報収集＋判断時間」をベースライン化し、
   「従来N分 → pmz自動判定M分」「誤承認1件の障害コストX時間」を**数値で**提示すべき。
   → §6 KPI（判定リードタイム・誤承認率）を「削減◯%」の物語に翻訳する。

2. **「人間/専門家の個性・規律を消さない」を差別化の中心に置く**【流用】
   ManabiyaAI が「既存AIは教師の個性を消す → 我々は保つ」で刺さったのと同型で、
   pmz は「既存CIゲートは“PM観点（要件＝プロダクトの意図）”を見ない → pmz は人間の受け入れ基準（正本）を尊重し、勝手に書き換えない」を前面に。
   pmz の設計インバリアント5（正本は人間確定）はまさにこの“個性/規律を消さない”思想と一致。ピッチで言語化価値が高い。

3. **包括フロー一気通貫の見せ方**【流用】
   ManabiyaAI は「授業ライブ → 教材 → テスト → FB」を一本のフローで見せた。
   pmz も「PR → シグナル収集 → 受け入れ基準照合 → Go/No-Go＋根拠コメント → 学習」を**1本のデモ動線**で見せると強い。

4. **公式LP/プロダクト化まで作ると“実現”軸（審査③）で勝てる**【検討】
   2位作品が LP まで用意していた。pmz も最低限のランディング/デモUI（GitHub Check の実画面）を用意すると「拡張性・運用性」評価で有利。ただし MVP スコープ（§2）を侵食しない範囲で。

5. **差別化の補強（pmz が上回れる点）**
   ManabiyaAI の弱点＝**効果が試算ベース・安全設計の言及が薄い**。
   pmz は「混同行列＋F-beta による before/after の客観計測」「決定論的ハードガード」「監査ログ」「プロンプトインジェクション多層防御」という**安全性・計測の厳密さ**を前面に出せば、同じ“賢いAI”でも“本番品質”で差別化できる。これは pmz 要件 §6.1/§7 の強みそのもの。

6. **学習ループの正当性に注意**【反面教師】
   ManabiyaAI の「教師FBを蓄積して個性を学習」は自己生成データの色がある。
   pmz は設計インバリアント6（自己生成ラベルで自己学習しない／正解は客観イベント由来）でこの罠を回避済み。
   ピッチでは「我々は自分の出力で学習しない＝モデル崩壊・確証バイアスを構造的に回避」と明言すると、学習系プロダクトとして一段上に見える。
