## ② 社会課題（なぜ刺さったか）

- **組織内の情報共有の非効率／情報サイロ**。一定規模以上の組織では、組織全体の出来事をキャッチアップするのが難しい。【確認済み】
- 従来の「社内報」は **情報収集と編集に多大な人手** がかかる（運用負荷が高くて続かない）。【確認済み】
- 分報（Slack times）・議事録・各種チャットに **価値ある情報が埋もれて流れていく**（フロー情報がストックされない）という痛み。【確度中／推測】
  - スニペットは「チャット・議事録を入力」と明言。pmzの観点でいう「散らばった情報を毎回かき集める」課題と同型。
- 審査基準 #2「**問題の明確さと解決策の有効性**」に強く噛み合う、**具体的で身近な課題設定**が評価された。【確度中】

## ③ 解決内容と主要機能

- **週次で社内の出来事を「新聞」として自動生成・配信**する。【確認済み】
- AIが **編集長（編集長ロール）** として振る舞い、複数の記事セクションを生成:【確度中】
  - 「業務トピック」【確度中】
  - 「社説（editorial）」【確度中】
  - 「今週の名言／週の名言」【確度中】
  > これらのセクション名は note.com 記事のWebSearch要約に由来。一次原文での厳密な表記は未確認。
- **複数データソースからの情報抽出・要約**（チャット＋議事録）を統合して紙面を構成。
  ハッカソンでは「複数データソース抽出によるマルチモーダル性」が評価ポイントとして言及された。【確認済み】
- 人手の編集を介さず、**定期バッチで自動的に1部の新聞が刷り上がる** 体験。【確認済み】

## ⑤ 技術的工夫ポイント

- **役割分担アーキテクチャ**: 「保存（Firestore）／スケジュール（Bun）／要約（Agent Builder）／執筆（Gemini）」を疎結合に分け、各段を再利用可能なコンポーネントとして設計。【確認済み】
- **2段階の言語処理**: Agent Builderで「要約候補の抽出」を先に行い、その上で Gemini が「編集長」として最終記事を執筆する **抽出→編集の二段構え**。生成の質と制御性を分離している。【確度中】
- **編集長メタファーをそのままプロンプト設計に落とす**: 「編集長」「社説」「業務トピック」「今週の名言」という新聞のロール/セクションを、生成タスクの分割単位として利用（出力フォーマットを安定させる効果）。【推測】
- **定期処理（週次バッチ）設計**: Bunをスケジューラに据え、人手なしで「毎週1部刷る」運用を成立させた点。継続的に回る（"まわす"）DevOps的なループ。【確認済み】
- **複数ソース統合**: 異種ソース（チャット＝断片的フロー情報 ＋ 議事録＝構造的ストック情報）を一つの紙面に編集統合。【確認済み】

## ⑥ デモ/UX（新聞メタファーの巧みさ）

- **「新聞」というメタファーが最大のUX上の発明**。【確度中（評価は推測込み）】
  - 生成AIの出力を「要約レポート」ではなく **紙面（社説・トピック・名言コラム）** として提示することで、
    読み物として親しみやすく、能動的に読みたくなる。情報共有が「義務」から「娯楽」に変わる。
  - 「のぞき見」という命名が、堅い社内報を **軽く・面白く** 見せるトーンを作っている（心理的ハードルを下げる）。
- デモは「自動で刷り上がった1部の新聞紙面」をそのまま見せる形が想定される（紙面レイアウトの具体は一次未確認）。【推測】
- 抽象的な「業務効率化AI」ではなく、**完成品（新聞）が目に見える** ため、審査・観客に伝わりやすい。プロダクトの価値が一目瞭然。【確度中】

## ⑧ pmz への学び

pmz（AIリリースゲートキーパー、PM観点でGo/No-Go判定）への流用戦術:

1. **「メタファーで出力を作品化する」戦術**（最重要の学び）。
   のぞき見新聞は生成結果を「新聞」に仕立てて価値を伝えた。pmzも判定結果を素のJSON/スコアでなく
   **「リリース判定の根拠レポート（号外/監査記事）」のような読み物メタファー** で提示すれば、
   PM観点という抽象価値が一目で伝わる。デモ映えに直結（pmz要件§6.1「デモは分かりやすく見せる」と整合）。

2. **抽出→編集の二段構え**は pmz の「客観シグナル抽出 → 判定文生成」の分離設計と同型。
   のぞき見新聞が Agent Builder（抽出）と Gemini（執筆）を分けたように、pmzも
   **「受け入れ基準への証拠抽出（決定論寄り）」と「Go/No-Go の言語化（LLM）」を層分離** する設計が支持される
   （pmz設計インバリアント#1「判定は構造化シグナルからのみ」と一致）。

3. **定期バッチ（Bun）で"まわる"ループを最小実装で見せた**点。pmzも自己改善ループを
   重厚に作り込む前に「週次 or イベント駆動で回る最小ループ」を先に動かして見せる戦術が有効
   （pmz §8.1 W2「見逃す→学習→検知」を最速で成立させる方針と同じ）。

4. **審査は"課題の具体性"を重く見る**（基準#2）。eCOINO/Manabiya/のぞき見新聞いずれも
   「誰の・どの業務の・どの痛み」を尖らせていた。pmzも「リリース判断者が散らばった情報をかき集める痛み」を
   抽象論でなく具体ペルソナで提示すべき（pmz要件§2.1のペルソナ表は強み、ピッチでも前面に）。

5. **差別化の置き方**: のぞき見新聞の差別化は技術でなく「PM/コミュニケーション観点」。
   pmzの差別化も同じく **「CIゲートが見ないPM観点（要件充足）」** にある。
   技術スタックの豪華さで勝負しない方が、本作の系譜では刺さりやすい（マルチエージェント体裁より"効いてる様子"優先＝pmz §8.1の注記と一致）。

6. **逆張りの注意点**: のぞき見新聞は「楽しい・読まれる」方向に振った。pmzは逆に
   **「止める・責任・安全」** が本質なので、メタファーは"娯楽"でなく **"監査・号外・差し戻し通知"** など
   緊張感のある方向に寄せるべき（トーンの取り違いに注意）。
