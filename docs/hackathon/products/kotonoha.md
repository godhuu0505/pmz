## ② 社会課題（誰のどんな痛みか）

スニペットから再構成（教育現場のテスト添削の負担と学習効果のギャップ）:

- **テストの「振り返り」が成績を左右する**が、現状の評価は多くが「採点（点数付け）」止まり。「言葉」によるフィードバック（添削）に転換できていない。【確度中：Benesse調査を引用と記載】
- 添削＝「良い考え方」と「誤りの原因」を丁寧に言語化することで、生徒の「強み」と「つまずき」が明確になり、**学習のPDCAが自然に回る**。フィードバックは生徒の成長に極めて重要。【確度中】
- 一方で添削は **教員の工数を圧迫**し、人手では全員に十分なフィードバックを返せない。＝「面倒を見てあげたい先生」の想いと現実のギャップ。【確認済み：タイトル＋スニペット】
- ペルソナは明確に二者: **復習したい生徒** と **手厚く見てあげたい教員**。両者の want を AI で同時に満たす設計。【確認済み】

> ドメイン全体の傍証: 増進会HD（Z会系）が塾向け「AI添削トレーニング」を展開、第一学習社「志望理由書 AI添削＋」等、AI添削は事業化が進む領域。＝**実需が確認できる市場**。【確認済み（業界事例）／『言の葉』との直接関係は無し】

## ③ 解決内容と主要機能

スニペットで確認できた機能（教育的配慮が随所に効いている）:

1. **手書き答案の読み取り（OCR的処理）**: Gemini に画像で答案を渡し書き起こす。【確認済み】
2. **「誤りを正さずそのまま書き起こす」プロンプト制御**: 「誤りを含む可能性があるため、正さずそのまま書き起こせ」と明示指示。これを入れないと Gemini が「よかれと思って」答案を勝手に正解化してしまう。**生徒の誤り自体が学習材料**なので原文保存が必須。【確認済み】★後述の pmz への学びの核
3. **添削コメントと答案箇所の対応付け**: 各コメントが答案の「どの部分」を指すかを特定して提示。【確認済み】＝根拠（該当箇所）の明示。
4. **Q&A（判断への問い返し）機能**: Gemini の添削判断に対し、生徒/教員が「なぜ？」と問い返せる。【確認済み】
5. **お気に入りコメントの保存**: 良い添削コメントを保存・再利用できる。【確認済み】
6. **模範解答は提示しない方針**（推定）: 業界の良質添削の定石（増進会も「模範解答を示さず助言のみ」）と、上記#2の思想から、`言の葉` も「正解を与えず気づきを促す」設計の可能性が高い。【推測】

> 設計思想の一貫性: 「AIが親切心で誤りを潰す」失敗モードを **プロンプトで構造的に封じ**、添削を「採点」でなく「言語化されたフィードバック」に振り切っている。教育プロダクトとして観点が鋭い。【確度中】

## ⑤ 技術的工夫ポイント

1. **「原文保存」プロンプトガード**【確認済み】: LLM の「親切な自動修正」という暗黙バイアスを、明示指示で打ち消す。**LLM のデフォルト挙動が課題ドメインに反する**ケースを見抜き、プロンプトで矯正した好例。
2. **コメント↔答案箇所の対応付け（根拠提示）**【確認済み】: 「どこに対する指摘か」を構造化。フィードバックの検証可能性・信頼性を高める。
3. **問い返し（Q&A）による human-in-the-loop**【確認済み】: AIの判断を一方通行にせず、ユーザが追問できる。教育文脈での「納得」を担保。
4. **観点別添削（推定）**【推測】: 「良い考え方」「誤りの原因」という軸でフィードバックを分けている記述があり、**観点分解された添削**の可能性。ただし「ルーブリック/評価観点の明示的分解」までやったかは未確認。

## ⑧ pmz への学び（流用できる戦術・差別化示唆）

pmz＝AIリリースゲートキーパー。`言の葉` の「観点別に根拠を引用して評価する」構造は **pmz の要件充足判定（§3.2.1）と本質的に同型**。具体的な転用:

1. **【最重要】「LLMの親切バイアスを明示プロンプトで殺す」設計を pmz にも適用する。**
   `言の葉` は「誤りを正さずそのまま書き起こせ」でLLMの自動補正を封じた。pmz では LLM が **PR diff の不備を『きっと意図通りだろう』と善意解釈してしまう**のが直接の脅威。→ 受け入れ基準チェックのプロンプトに「diff/PR本文の不足を補完するな。書かれていないことは『検証不能』とせよ」という**原文保存型ガード**を明示する。要件 §5 #2（3値＋棄権）の実装プロンプトに直結。

2. **「コメント↔該当箇所の対応付け」＝pmz の『証拠引用』の UX 化。**
   `言の葉` は各指摘が答案のどこを指すか紐付ける。pmz も各受け入れ基準の判定に **diff の該当行/該当ファイルを引用**する設計（§3.2.1「証拠を引用」）。→ GitHub Check のコメントで「この基準は `path:line` のこの変更で満たす/満たさない」と**箇所リンク**する UX を踏襲すると説得力が上がる（trace スキルの出力様式の参考）。

3. **「問い返し（Q&A）」＝条件付き自律の human-in-the-loop チャネル。**
   `言の葉` はAI判断に追問できる。pmz の「中リスク＝人間承認」（§3.4）で、**判定根拠に対し人間が問い返せる対話導線**を持たせると自律性と安全のバランスが取れる。棄権（検証不能）→人間エスカレーションの受け皿としても有効。

4. **差別化の示唆**: `言の葉` は「観点別フィードバック」を **教育＝主観領域**でやった。pmz は同じ枠組みを **リリース判定＝客観シグナル**でやる。pmz の強みは **客観ゲート（CI緑・ハードガード・正本基準）からのみ自律承認**という点（§7 #3/#5）。`言の葉` がプロンプト1枚で品質を担保するのに対し、pmz は **決定論的ハードガード＋監査証跡**で「LLMが覆せない壁」を持つ——ここを審査での差別化主張に使える（"PM観点の定性判断を客観軸へ射影"＝§1.1 のPMz）。

5. **ピッチ術の学び**: `言の葉` は「2ペルソナの想いを叶える」と**感情で課題を立てて**から技術に降りた。pmz も「リリース判断者/PM/オンコール」の痛み（§2.1）を**ナラティブ先行**で見せると、技術説明より刺さる。
