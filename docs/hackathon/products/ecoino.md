## ② 社会課題（誰のどんな痛みか）

- **痛みの本質**: サプライチェーンでは「計画」と「現実」が常にズレる。SNS の突発トレンドや
  想定外の天候など外乱で需給が動き、**欠品（売り逃し）や過剰在庫**といった損失が生じる。【確認済み】
- **意思決定の麻痺**: 製造業の現場では想定外が起きると**人が止まって意思決定できなくなり、責任の押し付け合い**が起き、
  結果として計画を変えられず損失が積み上がり続ける——この「変えられない／止まる」構造が本当の痛み。【確認済み】
- **ズレが見えない**: 計画と現実の「見えないズレ」が可視化されないまま放置される。【確認済み】
- ペルソナ: 需給計画担当・生産計画担当・SCMマネージャーなど、**現場で日々計画を回す業務担当者**。
  BI ツールや複雑なクエリの専門知識を持たない層も含む。【確度中】

## ③ 解決内容と主要機能

- **対話型 AI システム**で計画と現実のズレを**可視化し、迅速な軌道修正**を支援する。【確認済み】
- **シナリオ比較・対策立案支援**: 想定外イベントに対し、複数の対応シナリオを比較し対策を立案する。【確認済み】
- **止まらず回す体験**: 想定外が起きても**シミュレーションと計画修正を連続的に繰り返せる**ことで、
  「止まって損失を垂れ流す」状態を脱する。eCoino の強みは **人と AI エージェントの対話による
  納得感とラクさ**にあるとされる。【確認済み】
- **自然言語インターフェース**: Gemini による対話 UI で、業務担当者が複雑なクエリや BI 専門知識なしに
  AI の恩恵を受けられる。【確認済み】
- **データ取り込み → 分析パイプライン**: ユーザーが計画に必要な情報を **Google Drive にアップロード** →
  **Cloud Functions + dbt** で処理 → **Cloud Storage / BigQuery** に格納し、対話で問い合わせる。【確認済み】
- **将来構想**: ニュース・政治情報などを対応検討のトリガーに使い、Web スクレイピングで外部イベント
  （天候・SNS・ニュース）まで取り込み、より広いイベントに対応する展望。【確認済み】

## ⑤ 技術的工夫ポイント

- **構造化データ × 自然言語の橋渡し**: BigQuery 上の需給データに対し、LangChain + Gemini で
  自然言語クエリ／対話を可能にし、非エンジニアでも操作できる UX を実現。【確認済み】
- **データ取り込みの現場フレンドリー設計**: 専用システムでなく **Google Drive へのアップロード**を入口にし、
  dbt でモデリングして BigQuery に載せる——現場の既存ファイル運用に乗せやすい導線。【確認済み】
- **対話で「シナリオを回す」エージェント設計**: 単発 QA でなく、想定外 → シミュレーション → 計画修正を
  **対話で連続反復**できるループを中核に据えた（エージェントの必然性を業務課題で立てている）。【確認済み】
- **ドメイン知識の埋め込み**: SCM 専門家がチームにいることで、評価軸・シナリオ・対策の妥当性が現場目線で設計されている。【確認済み】
- **保守性/拡張性**: マネージドサービス中心（Cloud Run/Functions/BigQuery/Firebase）で
  小規模 PoC からデータ蓄積後の本格運用までスケールできる構成。【確認済み】

## ⑥ デモ／UX の見せ方

- **ストーリーテリングが秀逸**: 「**令和の米騒動**」のような**身近な事例から始まるストーリー**で問題意識を共有し、
  価値を効果的に伝えた点が評価された。【確認済み】
- **製造業をあえてテーマに選択**: 著者本人が「あえて製造業のテーマで取り組んだ。計画はズレるもの。
  完璧な計画より柔軟な現場を AI エージェントで作る」と発信。痛みの普遍性を訴求。【確認済み】
- **対話 UX の納得感**: 人と AI の対話による「納得感とラクさ」を体験価値の中心に据えた見せ方。【確認済み】
- **現場ユーザーテスト**: サプライチェーン業務に精通した社員からユーザーテストを受け、
  **実ユーザー視点を開発に取り込んだ**点が審査で高評価。【確認済み】

## ⑧ pmz への学び

pmz（AI リリースゲートキーパー：PR が要件を満たすか判定し Go/No-Go、結果から自己改善）への流用示唆。

1. **「人が止まる構造」を敵に設定すると刺さる**【確認済み起点】
   eCoino は「想定外で意思決定が止まり損失が積む」という構造的痛みを言語化して勝った。
   pmz も「リリース判断で**情報がかき集められず属人化し、見落としが障害になる**」という構造痛を
   ピッチの先頭に置くと強い（要件 §2.1 と整合。eCoino はこれを一文の物語に圧縮している）。

2. **身近な事例ストーリーテリングを1本仕込む**【確認済み起点】
   eCoino の「令和の米騒動」に相当する**具体的な失敗の語り**を pmz も用意すべき。
   pmz なら「DB マイグレーションを通して 24h 後に障害（型 i）」「"要件X対応"と言うのに diff が別物（型 ii）」を
   **名前付きの物語**として提示すると審査映えする（合成データ §9.1 のアークをそのまま"物語"として語る）。

3. **対話 UX で「止まらず回す」体験を見せる**【確度中】
   eCoino の核は単発判定でなく**対話で反復するループ**。pmz も Go/No-Go の単発出力でなく、
   「No-Go → 根拠 → 改善提案 → 再判定」の**対話的な往復**を見せると、エージェントの必然性が立つ。

4. **非エンジニア（PM）が触れる自然言語面を強みにする**【確認済み起点】
   eCoino は「BI/クエリ専門知識なしで使える」を差別化にした。pmz の **PM 観点（要件充足）**も
   「PM が SQL/CI ログを読まずに要件充足を対話で確認できる」面を前に出すと、PM ペルソナに直接刺さる。

5. **ドメイン専門家を巻き込んだ"現場ユーザーテスト"を証拠にする**【確認済み起点】
   eCoino は SCM 専門家＋現場テストで実用性点を取った。pmz は**実エンジニア/EM に触ってもらった所感**を
   提出物に載せると「本番品質」軸で効く。逆に pmz の差別化は**安全設計の規律**（ハードガード/権限分離/棄権）なので、
   eCoino にない「**誤承認を構造で抑える**」を pmz 固有の勝ち筋として強調する。

6. **GCP マネージド構成で"拡張性"を語る型は共通**【確認済み】
   eCoino: Cloud Run/Functions/dbt/BigQuery/Firebase。pmz も要件 §4.2 の Cloud Run/Gemini/Firestore/BigQuery を
   「小さく動かし、データが貯まれば本格運用」と同じ語り口でアピールできる。

7. **pmz だけの差別化を一段尖らせる**【推測】
   eCoino は「対話で賢く見せる」が、**時間軸の自己改善（学習で精度が上がる証拠）**までは前面化していない様子。
   pmz の Z 軸（before/after 混同行列・再発アーキタイプ検知率 100%）は eCoino が持たない**"賢くなる様子"の定量提示**。
   ここを最大の山場に据えれば、同系の優勝作と差別化できる。
