## ② 社会課題（対象とした痛み）

- 従来の旅行プランニングは、行き先・ルート・混雑・口コミ情報を**個人が手作業でかき集めて**組む必要があり負荷が高い。【確度中】
- 既存のAI旅行プランナーは「目的地・日数・予算」など**客観条件の入力**に寄っており、旅行者の **主観的な「雰囲気（vibe）/気分」** を起点にした提案が弱い。Vibe Planning はここを狙う。【確認済み】
- 提案の方向性として「効率化で計画の手間を消す」だけでなく、**「選ぶ楽しさ・自分だけの旅の物語を作るワクワク」を残す**ことを価値として打ち出している（計画を全自動で奪わない設計思想）。【確度中】

---

## ③ 解決内容と主要機能

- **「旅行の vibe（雰囲気・主観的な気分）」を起点に**、ユーザーの意図に沿ったスポット・ルートを提案する旅行プランAI。【確認済み】
- **リアルタイムの混雑データとレビュー（口コミ）データを分析**して、意図に合うスポット選定・経路生成を行う。【確認済み】
- **独自アルゴリズム**で「最適ルート」を生成（Vertex AI と Maps API の出力を独自ロジックで合成）。【確認済み】
- UX思想: ユーザーが「選択肢を選ぶ・味わう・自分の旅の物語を作る」体験に集中できる、新しいスタイルの旅程作成を志向。【確度中】

## ⑤ 技術的工夫ポイント

- **主観（vibe）→客観データへの接地**: 「雰囲気・気分」という曖昧な入力を、混雑データ・レビュー・トレンドという**測定可能なシグナルに翻訳**して提案に落とす設計。定性入力を定量データで裏取りする発想。【確度中】
- **複数データソースの統合**: Vertex AI（言語理解）＋ Maps（場所・混雑・経路）＋ Trends（話題性）を組み合わせ、単一LLM呼び出しでは出せない文脈判断を行う。**マルチソース統合＝エージェントの必然性**を満たす構成。【確度中】
- **独自ルートアルゴリズム**: LLM任せにせず、経路最適化を独自ロジックで担保（LLMの弱い領域＝厳密な最適化を決定論的に補強する分業）。【確認済み（存在）／中身は未確認】
- **エージェント設計（対話 vs 自律）**: 対話で意図を引き出すのか自律で一括提案かは一次資料未取得のため未確認。【推測】

## ⑧ pmz への学び

pmz＝AIリリースゲートキーパー。畑は違うが、ハッカソン受賞作としての戦術は流用できる。

1. **「主観→客観シグナルへの接地」は pmz の核と同型**。
   Vibe Planning は「気分（主観）」を混雑・レビュー・トレンド（客観データ）に翻訳した。pmz は「PM観点（要件充足という定性判断）」を**客観シグナル（CI結果・受け入れ基準・リスクフラグ）に射影**して測る（要件 §1.1 の "PMz＝z成分へ射影"）。**この"定性を定量に落とす"物語はピッチで刺さる**ことが3位入賞で裏付けられた。pmz もこのフレーミングを前面に出すべき。

2. **LLM＋決定論ロジックの分業が評価される**。
   Vibe Planning は経路最適化を「独自アルゴリズム」で担保しLLM任せにしなかった。pmz の **決定論的ハードガード**（§7 #5・db_migration/auth/payment はLLM確信度に関係なく自律承認禁止）はまさに同じ思想で、「LLMが覆せない壁を別に持つ」点を**設計の堅牢性アピール**として強調できる。

3. **感情価値・物語性が点を取る**。
   Vibe Planning は「効率化で計画を奪わず、選ぶ楽しさを残す」という感情ナラティブで差別化した。pmz も「障害で同じ失敗を繰り返す痛み → 学習して賢くなるゲートキーパー（Z軸）」という**ビフォーアフターの物語**（§9.1 のアーク・"見逃す→学習→検知"）を、指標だけでなく**人間の痛みの物語として語る**のが効く。

4. **差別化の角度を一語で言い切る**。
   レッドオーシャン（旅行AI多数）でも「vibe」の一語で立ち位置を作った。pmz も「PM観点」「Z軸（自己改善）」を**一語の旗**として一貫使用する戦略（既に §1.1 で言語化済み）は正しい。ピッチの最初の一文で旗を立てる。

5. **マルチソース統合＝エージェント必然性の証明**。
   単一LLM呼び出しでは出せない統合判断であることが、審査の「エージェントの必然性」に効く。pmz も code+CI+要件充足の**マルチソース統合**を必然性の論拠として明示する（要件 §2.2 と整合）。

6. **逆張りの差別化軸**: Vibe Planning が「旅行（誰でも分かる・デモ映え）」で勝負したのに対し、pmz は「DevOps×PM観点」という**より専門的で前例の少ない領域**。新規性では有利だが**課題の伝わりにくさ**がリスク。Vibe Planning のように「誰でも30秒で痛みが分かる導入」を冒頭に作る工夫（例: "障害を通したリリースを後から振り返る無力感"）を借りるべき。
