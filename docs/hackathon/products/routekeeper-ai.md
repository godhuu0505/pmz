## ② 社会課題

【確認済み】
- 日本では**年間およそ30万件の交通事故**が発生している、という導入。
- そのうち多くは「**危険箇所を事前に知っていれば防げた**」事故であるという問題提起。
- 解こうとする痛み: ドライバー／歩行者が、これから通る経路上の危険を**事前に把握できない**こと。
  既存のナビは「最短・最速」を出すが「**その道のどこが危ないか**」は教えてくれない、という空白を突く。

【推測】
- 高齢者・子ども・初めて通る道のユーザーなど「土地勘のない移動」での事故低減を含意している可能性。
  （スニペットでは明言なし。当方推定。）

## ③ 解決内容・主要機能

処理パイプライン（【確認済み】の流れ）:

```
出発地・目的地を入力
   ↓  Google Directions API で経路取得
   ↓  経路に沿って 50メートル間隔で Street View 画像を収集
   ↓  各画像を Gemini 2.0 Flash の画像理解で解析（構造化プロンプト）
   ↓  危険要因をスコアリング → 地図上に危険スポットとして可視化
   ↓  AIチャットボットが安全アドバイスを提示
```

主要機能:
1. **経路ベースの危険スキャン**【確認済み】 — Directions API で得た経路を **50m 間隔**でサンプリングし、
   各地点の Street View 画像を取得して解析。
2. **マルチ観点の危険判定**【確認済み】 — 1枚の画像を複数の安全観点から評価:
   - 交差点の構造・**死角（blind spots）**
   - **路面状態**（穴・濡れ・劣化）
   - **視認性**（信号・標識・見通し）
   - **歩行者・自転車の横断リスク**
3. **危険スコア／危険スポットの地図可視化**【確度中】 — 解析結果を地図上のマーカー等で提示
   （「危険スポットの可視化」はスニペットで確認、マーカー形式は推定寄り）。
4. **AIチャットボットによる安全アドバイス**【確認済み】 — 経路解析の後段で、対話形式で
   その経路の注意点・助言を返す。
5. **デモ動画**【確認済み】 — 「経路解析→危険箇所可視化→AIチャットボット安全アドバイス」の
   一連の流れを通したデモ動画を用意。

## ⑤ 技術的工夫ポイント

【確認済み】
- **「経路 → 離散サンプリング → 画像LLM解析 → 集約」というパイプライン設計**。連続した道路を
  50m 間隔の離散地点に落とし、各点を独立に Gemini にかけて危険要因を抽出する構造。これにより
  「経路全体の危険プロファイル」を機械的に組み立てている。
- **構造化プロンプトによる観点固定**。交差点死角／路面／視認性／横断リスクという**観点を事前定義**して
  画像を評価させ、出力をスコア化。プロンプト側で評価軸を固定することで、出力のばらつきと
  ハルシネーションを抑える狙い（pmz の「受け入れ基準の構造化」と発想が近い）。
- **既存の公開データ資産（Street View）の再利用**。専用センサーやIoTを置かずに、Google が持つ
  路面画像を「危険予知の入力」に転用した点が低コスト・即スケールにつながる。

【確度中／推測】
- 50m という粒度は「解析コスト（API課金・LLM呼び出し数）」と「見落とし」のトレードオフを
  踏んだ設計値と推測（明示の根拠説明はスニペット未確認）。
- 経路全体を扱うため、地点数×画像取得×LLM呼び出しが線形に増える。**バッチ/並列化や
  キャッシュ**の工夫があったと推測されるが未確認。

## ⑥ デモ／UX

【確認済み】
- **入力 → 経路解析 → 危険箇所可視化 → AIチャットボット助言**という一気通貫のフローを
  **デモ動画**で提示。「使うと何が起きるか」が一目で伝わる構成。
- 地図上での危険スポット表示 ＋ 自然言語チャットの二段構え。**定量（スコア/地図）と
  定性（チャット助言）**を組み合わせて、ユーザーが行動に移せる形にしている。

【推測】
- 一般ユーザー（ドライバー/歩行者）がそのまま触れる Web UI と推測。社会課題の身近さ＋
  地図ビジュアルで**審査員へのデモ映えが強い**タイプ。

## ⑧ pmz への学び

pmz（AIリリースゲートキーパー）への流用可能な戦術:

1. **「観点を構造化プロンプトで固定」は共通の正攻法**【確認済み起点】。
   RouteKeeperAI は危険を4観点に固定して画像LLMを安定化させた。pmz の「受け入れ基準を構造化して
   満たす/満たさない/検証不能で評価」(§3.2.1) と同型。**観点固定＝ハルシネーション抑止**という
   メッセージは審査で伝わる、という裏付けになる。pmz もプロンプト設計の「観点固定」を前面に出すべき。

2. **離散サンプリング→個別判定→集約という構造はデモ映えする**。
   RouteKeeperAI の「経路を50m刻みで点に落として各点を判定し、全体プロファイルを作る」は、
   pmz の「PR を受け入れ基準ごとに分割→各基準を証拠引用付きで判定→Go/No-Go に集約」と発想が一致。
   **"分割して各々に根拠を付け、最後に統合する"流れを可視化**すると分かりやすい（pmz の判定レポート UI に活かす）。

3. **定量（スコア/地図）＋定性（チャット助言）の二段提示が刺さる**。
   pmz も **判定（Go/No-Go＋確信度）の定量** と **根拠コメント＋改善提案の定性** を併置する設計
   （§3.4）。RouteKeeperAI の受賞は、この「数値＋自然言語助言」の組合せがUX上強いことを示す。
   pmz は「混同行列/精度推移（定量）」＋「No-Go の理由・改善提案（定性）」の見せ方を磨くと良い。

4. **差別化の軸**: RouteKeeperAI は単発のマルチモーダル解析が中心で、**自己改善（時間軸の学習）が
   見当たらない**。pmz の最大の差別化＝**Z軸（結果から学習して賢くなる）**（§1.1, §3.3）は、
   この優秀賞群が持っていない強み。「**賢くなる様子をbefore/afterで見せる**」(§6.1) を死守すれば、
   "良くできたマルチモーダルデモ"を超えられる。**自己改善デモを最優先**という現方針は正しい。

5. **コスト/精度の弱点を先回りで潰す**。RouteKeeperAI は API 従量コストと Street View 鮮度・
   精度検証が弱点として残った。pmz は**評価セットでの混同行列・回帰テスト**(§3.3, §6.1) を
   武器に「精度を客観計測している」ことを示せば、ここで明確に上回れる。

6. **社会課題の"つかみ"を1つの数字で**。RouteKeeperAI の「年間30万件」は強いフック。pmz も
   「リリース起因のインシデント／誤承認のコスト」を**1つの具体数字**で冒頭に置くとピッチが締まる。
