## ② 社会課題

- **対象ペルソナ**: 社会福祉士（ソーシャルワーカー）。支援が必要な利用者に寄り添う専門職。【確認済み】
- **痛み1: アセスメント入力の事務負荷**。利用者1人あたり**1〜2時間**かかるアセスメント入力業務が重い。
  初回アセスメント作成の負担が、利用者に向き合う時間を奪っている。【確認済み（検索スニペットで時間も一致）】
- **痛み2: 支援制度（社会資源）の複雑さ・属人性**。利用者の状態に合う支援制度を探し、適切に組み合わせる作業は
  制度知識に依存し属人的。新人や多忙な現場では取りこぼしが起きる。【確度中】
- **痛み3: 多ケース・連絡コスト**。支援制度の活用には関係機関への連絡・タスク管理が伴い、
  ケース数が増えるほど社会福祉士の事務作業が膨らむ。【確度中】
- **背景にある構造課題**: 福祉現場の人手不足。事務作業を削って「人にしかできない支援」に時間を回したい、
  というのがプロダクトの動機。【推測（一般的な業界文脈と整合）】

> pmz 視点メモ: 「専門職が散らばった情報をかき集めて判断している」という痛みの構造は、
> pmz が狙う「リリース判断者が PR/CI/要件を毎回かき集めて判断している」とほぼ相似形。
> フクシアは“福祉の事務”、pmz は“リリースの事務”を肩代わりする、と同じ語り口で説明できる。

## ③ 解決内容と主要機能

中核は **2つの専門エージェント**で社会福祉士の業務フロー（アセスメント→支援計画→タスク化→連絡）を支援する。【確認済み】

1. **アセスメント作成エージェント**【確認済み】
   - 社会福祉士と利用者の**会話ログを解析**し、アセスメント項目を**自動で穴埋め**する。
   - 1〜2時間かかっていた初回アセスメント入力を大幅短縮するのが価値訴求の柱。
2. **支援制度提案エージェント**【確認済み】
   - **社会資源 RAG（ソーシャルリソース RAG）**から利用者に適した支援制度を検索・提案。
   - 提案を**タスク化**して社会福祉士のタスク管理を支援（単なる検索で終わらせない）。
   - **自律的に追加質問**: 入力情報をもとに必要なタスクを自律提案し、足りない情報は自動で追加ヒアリングする。
   - **関係機関への連絡機能**（現状は**モック**）: 登録後に関係機関へ連絡し、制度活用時の連絡コストを削減。【確認済み】
3. **多ケース負荷管理 / タスク管理**【確度中】
   - 支援制度提案をタスク化することで、ケースごとの「次にやること」を可視化・管理。
   - ※「複数ケースをまたいだ負荷ダッシュボード」までを一次資料で断定はできない。タスク化＝負荷管理の入口。
4. **ITに不慣れな現場向けの簡単UX**【確認済み】
   - 「IT に親しみのない現場でも導入しやすい、わかりやすいシンプルな UX」を明示的に設計目標に掲げている。

## ⑤ 技術的工夫ポイント

- **役割分担した2エージェント構成**: 「アセスメント作成」と「支援制度提案」を分離し、
  業務フロー（記録→計画→実行）に沿って責務を切った。単一巨大プロンプトでなく専門エージェントに分割。【確認済み】
- **自律的な追加ヒアリング**: 支援制度提案エージェントが、入力情報の不足を自分で検知し追加質問を投げる
  ＝マルチステップの自律調査（エージェントの必然性を体現）。【確認済み】
- **RAG で“制度知識の属人性”を解消**: Vertex AI RAG Engine + 社会資源データで、
  制度検索を知識ベース化。CSE で外部情報も補完。【確認済み】
- **提案→タスク化→連絡の一気通貫**: 「探して終わり」でなく、タスク登録・関係機関連絡（モック）まで
  ワークフローを閉じる設計。エンドツーエンドの“業務代行”に踏み込んでいる。【確認済み】
- **AI駆動開発の規律**: monorepo を `application/AGENTS.md` / `frontend/AGENTS.md` に分け、
  各パッケージのルール（Ruff 120桁、日本語コメント必須、PR タイトル `[application]/[frontend]` 形式、
  push前に lint+format+build）を AGENTS.md に集約。**開発は Cline / GitHub Copilot / Codex 併用を前提**とし、
  `.clinerules` を AGENTS.md へのシンボリックリンクで共通化。【確認済み（README/AGENTS.md raw）】
  - ※「Gemini CLI 併用」は今回の一次資料（README/AGENTS.md）では明示確認できず。
    Cline・Copilot・Codex は確認済み。Gemini CLI は【確度中（依頼者情報・状況証拠ベース）】。

> pmz 視点メモ: 「複数コーディングエージェントを AGENTS.md という単一フォーマットで束ね、
> シンボリックリンクで各ツールに配る」は pmz の `.claude/` ハーネス運用にそのまま流用できる。
> pmz は CLAUDE.md 中心だが、Codex/Gemini CLI も使うなら AGENTS.md→各ツール config への symlink で一元化する手が有効。

## ⑧ pmz への学び（AIリリースゲートキーパー）

フクシア（2専門エージェント）と pmz（4体構成志向: Orchestrator + CodeRisk + PM/Req + Retrospective）への具体的示唆。

1. **「専門職の事務をエージェントが肩代わり」という勝ち筋をそのまま借用できる**。
   フクシア=福祉の事務、pmz=リリース判断の事務。pmz のピッチを「テックリード/EM が毎回かき集めている
   PR/CI/要件の照合作業を肩代わりする」と、フクシアと同じ“痛み定量化→肩代わり”の型で語ると刺さる。【流用可】

2. **エージェント数より「業務フローに沿った責務分割」が評価される**。
   フクシアは2体だが、記録→計画→タスク化という業務動線で割った。pmz の4体も「体数」より
   「PRゲートの判断動線（コードリスク評価→要件充足判定→統合判断→振り返り学習）」に沿っている説明を前面に。
   §8.1 で「逼迫したら4エージェント化を削ってでも自己改善デモを守る」とした判断は、フクシア（2体で最優秀）が裏付ける。【流用可】

3. **「自律的に追加質問する」＝エージェントの必然性の見せ方**。
   フクシアは情報不足を自己検知して追いヒアリングする。pmz でも「受け入れ基準が PRからは検証不能 →
   断定せず人間にエスカレーション」（要件§3.2.1の3値＋棄権）を、“賢く迷う自律性”としてデモで強調すると効く。【強化示唆】

4. **RAG で“属人知識”を構造化する発想**。
   フクシアは制度知識を社会資源RAG化。pmz は「正本（canonical acceptance criteria）」と
   「過去の誤判定ケース/ルールブック」を Few-shot 検索源として持つ（§3.3.1）。
   これはフクシアの社会資源RAGと同じ“暗黙知の知識ベース化”であり、デモで同型に見せられる。【流用可】

5. **デモは「効果が一目で分かる前後ショートカット」を最優先**。
   フクシア=「会話ログ入れたら埋まる」。pmz=「同型の地雷リリースを、学習前は見逃し→学習後は検知ブロック」
   （要件§9.1 のアーク）。pmz の自己改善 before/after グラフは、フクシアの“作業時間短縮”より
   さらに強い「賢くなる様子」を見せられる＝pmz の差別化を最大化すべき箇所。【強化示唆】

6. **非IT/本番志向のUXと“正直さ”が効く**。
   フクシアは連絡機能をモックと明記しつつ提出。pmz も「合成データの correct_verdict は正解を仕込める前提で
   実運用では成立しない」と正直に明記する設計（CLAUDE.md §5-7）と同じ誠実さ。審査での信頼につながる。【整合確認】

7. **AGENTS.md 共通フォーマット運用の流用**。
   フクシアは Cline/Copilot/Codex を AGENTS.md + symlink で一元化。pmz が複数コーディングエージェントを
   使うなら、CLAUDE.md を正とし AGENTS.md / 各ツール config を symlink で同期する運用を `.claude/README.md` に追記する価値あり。【運用流用可】

8. **差別化の念押し**: フクシアは「業務代行（やってくれる）」型。pmz は「判定＋自己改善（賢くなり続ける）」型で、
   フクシアにない**Z軸（時間方向の精度向上）**を持つ。フクシアが取れなかった“LLMOps/評価サイクル”の映えは
   pmz の独自スコープ（要件§3.3）。フクシアを「実用×やさしさで勝った前例」と位置づけ、
   pmz は「実用＋自己改善（賢くなる証明）」で上書きする、という対比でピッチを組むと強い。【戦略示唆】
