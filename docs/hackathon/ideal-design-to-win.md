# GateKeeper 理想設計 ── 「リソース無制限で勝ちにいく」版

> ステータス: **ビジョン／たたき台**（MVP要件の代替ではない）
> 位置づけ: `docs/requirements.md`（正本・MVP）で意図的に削った要素を、審査で勝つ前提で
> 「理想形」として復元・拡張したもの。実装の取捨選択は §8.1 の優先順位が引き続き優先する。
> 作成日: 2026年6月14日

---

## 0. このドキュメントの狙い

MVP（要件定義書 §8.1）は「1人・4週間」という現実制約から逆算した**最小の心臓**を定義している。
本書はその制約を一旦外し、**「課題の新規性 / 解決策の有効性 / 実装品質と拡張性 / DevOpsサイクル」
の4審査軸を一段超えるなら何を作るか**を理想論として描く。MVPを否定するものではなく、
「どこを前倒しすると最も審査に効くか」を判断するための北極星とする。

結論（賭けの一行）:

> **「自己改善が"本物"だと証明できる閉ループを、生きたGitHubリポジトリ上でライブに回す。」**
> 合成データは"わかりやすさ"のためのデモ補助に格下げし、主役を実データに移す。

---

## 1. コアの賭け ── 合成データから「卒業」する

MVPは `correct_verdict` を仕込んだ合成 ~24 件で before/after を見せる（§9.1）。これは再現性が高く
正直だが、構造的な弱点がある ── **「それ、そう作っただけでは?」**（§6.1 で自分でも警戒している循環性）。

理想形は**二段構え**でこの批判を封じる:

| 役割 | 何で見せるか | 狙い |
|------|--------------|------|
| **主役（説得力）** | 実在リポジトリ（OSS or 自前）に GateKeeper を常駐させ、過去 N 百件のマージ済み PR を**タイムマシン再生**。障害を起こした PR（後続に revert/hotfix がある）を客観イベントから自動ラベリングし、時系列順に判定→学習→後半で同型を検知、を**仕込みなしで**実演 | 「新規性」「有効性」を実データで裏取り |
| **脇役（わかりやすさ）** | 手作りアーク ~24 件を「型(i)(ii)が3幕で進む紙芝居」として残す（§9.1 のまま） | 90 秒で構造を理解させる |

**設計原則**: 合成で語り、実データで裏取りする。この役割分担が新規性と実装品質を同時に満たす最大のレバー。

## 2. アーキテクチャ理想形 ── フル6エージェント + 「賢さの源泉」を独立化

MVP は 4 体（Orchestrator + CodeRisk + PM/Req + Retrospective）。理想は **OpsMetric と Memory/RAG を
独立エージェント化**して 6 体にする。

```
                    ┌──────────────── Orchestrator ────────────────┐
                    │  調査計画 → 並列ディスパッチ → 統合 → 判定     │
                    └──┬───────┬────────┬────────┬────────┬────────┘
        ┌──────────────┼───────┼────────┼────────┼────────┴──────────┐
        ▼              ▼       ▼        ▼        ▼                   ▼
    CodeRisk      TestSignal OpsMetric PM/Req  Retrospective    ★Memory/RAG
    diff/AST解析   CI/カバレ  本番監視  要件充足 障害振り返り     判例検索エージェント
```

理想形での強化点:

- **★Memory/RAG を独立コンポーネント化**: 「過去の誤判定を引いてきて今の判定に効かせる」という
  自己改善の動脈を、トレース上で**可視化できる単位**にする。審査の「どこが学習してるの?」に一撃で答える。
  **本書で MVP に前倒しすべき最優先候補**（§7 参照）。
- **CodeRisk に AST/セマンティック解析**: 正規表現のリスクフラグから卒業。`db_migration / auth / payment`
  を文字列マッチではなく、実際の migration ファイルや権限チェック関数の変更を AST/CodeQL 的に検出。
  → 決定論的ハードガード（要件 §7 #5）の信頼性が段違いになる。
- **OpsMetric を本番 Cloud Monitoring + Four Keys(BigQuery) に実接続**: デプロイ前ゲート②を実装し、
  2 段ゲート（要件 §3.1）を本当に通す。

## 3. 自己改善ループを「ガバナンス付きで本当に回す」

要件 §3.3.1 で設計だけして MVP では簡易化した部分を全実装する。ここが審査の山場（LLMOps）。

1. **ルール自動進化 → 回帰ゲート必須通過**
   振り返りエージェントが新ルール提案 → ラベル付き評価セットで**バックテスト** →
   「誤承認↓ かつ 誤ブロック非悪化（F-beta 改善）」を満たすルールだけ自動マージ。
   落ちたルールは人間レビュー行きの PR に。
   **ルールブック自体を Git でバージョン管理し、ルール追加も PR で来る**
   （= GateKeeper が自分のルールを自分のゲートに通す自己言及）。
2. **評価データセットを二層に**
   ① 学習に使う実データ ② 学習に**絶対使わない**ホールドアウトの LLM 生成評価セット。
   プロンプト/モデル変更のたびに CI で回帰テストし、混同行列を PR コメントへ自動投稿。
3. **ルールの庭師ジョブ**
   発火率・的中率で死にルールを剪定、意味的重複を embedding 類似度で統合。
   「ルール数が無限に増えて破綻する」批判を先回りで潰す（要件 §3.3.1 (4)）。

## 4. 「本番品質」を演出する3点セット（差がつくところ）

要件 §7 の安全設計を"見える化"する。

- **改ざん不能な監査証跡**: 全判定（入力ハッシュ / 確信度 / 根拠引用 / 発火ルール ID / モデルバージョン /
  プロンプトバージョン）をハッシュチェーンで連結。「なぜ通したか」を後から完全再現・巻き戻し可能に
  （要件 §7 #4 の責任分界そのもの）。エンタープライズ感が出る。
- **OpenTelemetry で全エージェントを分散トレース**: Cloud Trace 上で
  「オーケストレータ→各サブ→Memory 検索→統合」のスパンを可視化。
  エージェントの必然性（マルチステップ自律）を**証拠つきで**主張できる。
- **fail-to-human の実演**: デモ中にわざと LLM API を落とし、ブロックも素通りもせず人間レビューへ
  縮退する様子を見せる（要件 §7 #2）。「壊れ方まで設計してある」は本番品質の最強アピール。

## 5. デモ脚本（勝ちパターン）

審査は記憶に残った作品が勝つ。理想のデモは **90 秒で「賢くなる」を体感**させる:

1. **同じ型の PR を2回投げる**。1回目（学習前）→ 見逃して Go → 後続で revert 発生 → 自動で「誤承認」ラベル。
2. 振り返りエージェントがルールを起票 → 回帰テスト通過 → ルールブックにマージ（画面で見せる）。
3. **2回目（同型 PR）→ Memory 検索が1回目の失敗事例を引く → No-Go +「前回これで障害が出た」と
   根拠引用つきでブロック**。
4. before/after 混同行列と DORA 時系列を並べ、「誤承認↓・誤ブロック不変」を1枚で。

この「**見逃す→学習→次は捕まえる**」が目の前で1ループ回るのが、他の CI ゲート系作品と
決定的に差がつく瞬間。

## 6. 究極の"映え" ── メタレベルの自己言及

**GateKeeper のリポジトリ自体を GateKeeper が守る**。自分の PR に自分で Go/No-Go を出し、
自分の判定ロジック変更を自分の回帰テストで検証する。テーマ「まわす」に対し、
**ツールが自分自身で DevOps サイクルを回している**二重構造（要件 §5）を、スクショ1枚で証明できれば
新規性・必然性・DevOps 充足を一撃で取れる。

---

## 7. 優先度 ── 理想から「今 MVP に効くもの」を1つ選ぶなら

理想要素の審査インパクト順:

| 順位 | 要素 | 理由 |
|------|------|------|
| ① | **実データ閉ループ**（§1） | 説得力。循環性批判を構造的に封じる |
| ② | **Memory/RAG 独立化 + ライブデモ脚本**（§2, §5） | 映え。自己改善の動脈でデモの心臓。実装コストが比較的軽い |
| ③ | **回帰ゲート付きルール進化**（§3） | LLMOps の証明 |
| ④ | **監査 + 分散トレース**（§4） | 本番品質 |

**MVP に前倒しで1つだけ入れるなら ②（Memory/RAG エージェント独立化）を推す。**
自己改善の動脈であり、デモの心臓であり、かつ実装コストが軽いため。

## 8. 要件定義書（正本）との関係

- 本書は **ビジョン**であり、実装の取捨選択は要件 §8.1 の週次優先順位が引き続き**優先**する。
- 本書の要素を採用する場合は、まず該当する要件 § を更新し、必要なら `grill-me` で論点を詰めてから
  実装する（CLAUDE.md §6 の仕様駆動を踏襲）。
- スコープ外は据え置き: コスト管理機能（要件 §5 / §10）は理想形でも今回は扱わない。
